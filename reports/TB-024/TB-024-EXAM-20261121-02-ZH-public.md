## 执行摘要

本报告分析 MCP 工具 mcp-ssh-manager 的一起审批展示完整性事件：其 `ssh_deploy` 工具的 `restart` 选项会在远端服务器上以 SSH 用户身份按原文执行为 shell 命令，但人审审批卡上不显示该命令——卡面只读工具名、「Destructive」与「(no command)」，部署文件与其目标路径同样不展示。据仓库级公告 GHSA-vx67-5jmh-4xq2 原文（本拍实读全文），机理在于展示层与执行层脱钩：审批引擎把完整请求（参数齐备、秘密已移除）发给界面，界面却只渲染 `command` 字段，而部署请求没有该字段，于是批准者在看不到实际内容的情况下批准，批准后即执行未展示的 `restart` 命令。当 MCP 客户端可被提示注入等方式 steer、且服务器审批设为 `destructive` 或 `always` 时，被 steer 的智能体可借一次部署请求夹带任意命令获批执行。受影响版本为 >=3.0.0、<=4.3.0（版本上限为考卷线经仓库 advisory API 实读的转引，见第八节 G-01），4.3.1 修复；本件已核材料未列 CVE 编号，严重度为中危（moderate）。（注：分诊原表记「无 CVE」，仅指已核材料未列，非断言不存在 CVE 编号；分诊分不因此改动。）

## 关键发现

- **KF-01 机理成立：审批展示与实际执行脱钩，批准者批准的是自己看不到的内容。** 引擎发送完整请求、界面只显示 `command` 字段；部署请求无该字段，卡面只剩工具名、「Destructive」、「(no command)」，`restart` 命令与部署文件、目标路径均不展示；批准后执行的正是未展示的 `restart` 命令。任何无命令行的请求都以同样方式展示。（已验证，一手源：GHSA 公告 Summary／Details 段原文）
- **KF-02 `restart` 本就是命令且未加引号直入远端命令，但成漏洞的是审批而非命令语义本身。** 公告 Details 段载：`src/deploy-helper.js` 中 `restart` 未经引用处理进入远端命令（path、owner、permissions 自 3.8.6 起已引用），报告者给出的构造值可在服务器建文件、公告称可复现（具体构造细节本稿不复述）。但公告明确定性：`restart` 按 Deployment Guide 一贯是命令、引用化会破坏既有部署，且同一攻击者在 `unrestricted` 服务器上本可经 `ssh_execute` 执行任意命令——使之成为漏洞的是审批环节的不可见。（已验证，GHSA 公告 Details 段；复现为报告者结果、我方未复现，见第八节 G-04）
- **KF-03 利用条件收窄且边界明确。** 仅当服务器 approval 设为 `destructive` 或 `always`、且 MCP 客户端可被 steer（如智能体读到的内容中的提示注入）时成立；无审批时相对 `ssh_execute` 无增益；`readonly` 与 `restricted` 服务器整体拒绝 `ssh_deploy`。（已验证，GHSA 公告 Impact 段）
- **KF-04 覆盖判定为未覆盖：现头无审批展示完整性检查。** 核验钉 20 插件清单中无任何检查以「审批展示内容」与「实际执行内容」两面证据做一致性判定。（已验证，静态核验，核验钉 89a65525）
- **KF-05 本件为新类别新缺口 SE24，不是已有缺口的新事件。** 考卷库此前无「审批展示不完整」类别；拟建检查 v19.approval.display_execution_mismatch 已入 loop backlog 在队区，本稿不预判其落地形态与覆盖。（已验证，考卷库标准段＋loop backlog SE24 条）
- **KF-06 修复与缓解路径明确且有一手指针。** 4.3.1 起审批卡对无命令行的请求展示其参数（文件、目标路径、`restart` 命令，秘密已移除），`restart` 保持命令语义、工具描述与指南已改明；升级前缓解：不批准卡面为「(no command)」的请求、无部署业务的服务器保持 `readonly`／`restricted`、或关闭 `advanced` 工具组。（已验证，GHSA 公告 Patches／Workarounds 段＋v4.3.1 发布说明）

## 三、技术分析

### 3.1 机理：展示面与执行面脱钩，审批防线在「所见」一环失效

据 GHSA 公告原文，本件机理分三层：

- **工具语义层**：`ssh_deploy` 的 `restart` 选项按 Deployment Guide 一贯是「在服务器上按原文执行的 shell 命令」，但工具描述却称之为 service——语义标注与实际行为先已不一致。
- **传输层**：审批引擎把整个请求（含全部参数、秘密已移除）发送给审批界面，执行面将按这份完整请求行事。
- **展示层**：界面只显示请求中的 `command` 字段。部署请求没有该字段，于是卡面只呈现工具名、「Destructive」与「(no command)」——`restart` 命令、部署文件与其目标路径全部缺席。审批人点下批准，执行的正是其未见过的 `restart` 命令。

定性要点：缺陷不在命令构造（`restart` 是命令本为设计语义），而在**人审环节的所见与所批脱钩**——human-in-the-loop 审批作为提示注入防线，其有效性以前提「审批人能看到自己批准的全部执行内容」为条件；展示不完整使该防线形同虚设（考卷库影响面段口径）。公告同时载明同一展示逻辑适用于一切无命令行的请求，不限于 `ssh_deploy`。

### 3.2 利用条件

- 目标服务器的 approval 须设为 `destructive` 或 `always`（即部署请求会进入人审审批）；
- MCP 客户端（智能体）须可被 steer——公告举例为智能体读到的内容中的提示注入，使其在部署请求中夹带自备命令；
- 服务器权限档须非 `readonly`／`restricted`（该两档整体拒绝 `ssh_deploy`）；
- 边界：未开启审批时，能调用 `ssh_deploy` 的智能体在 `unrestricted` 服务器上本就能经 `ssh_execute` 执行任意命令，本件不带来增益——本件的增量风险恰在「有审批」场景：审批本应拦下的内容因不可见而被放行。

### 3.3 与同类事件的关系

本件与考卷库内既有命令注入类条目的区别在判定面：注入类判「命令如何被构造」，本件判「人审所见与实际执行是否一致」——同一执行面、不同防线层。同产品 mcp-ssh-manager 另有两件命令注入公告（GHSA-4jx9-2fwj-pg4j 数据库助手命令注入、GHSA-qwwm-vrm9-4mw8 备份子系统命令注入，仓库级首发分别为 2026-07-12 与 2026-08-28，本考卷窗不收、记名备查，见当日总结剔除说明），说明该产品命令执行面反复出事，但本件类别（审批展示完整性）与之不同。本稿只作类别层面对照，不对其他条目的判定作任何追认或改判。

### 5.2 为何未覆盖：缺哪一类检查

本展品需要的检查形态（即考题判定要求）：对带人工审批环节的工具执行面，引用审批展示与实际执行两面证据判定——

- **应判 fail**：审批展示漏显安全相关内容——实际执行命令／关键参数中的安全相关部分未展示（占位或省略；经定义的无害脱敏不属漏显）而执行面按未展示内容执行，且展示侧与执行侧证据齐备、同属一次审批的绑定成立（本件本体按公告记述属此格）；绑定或任一侧证据不足者不入此格、入 inconclusive 格；
- **应判 pass（不误报）**：同一次审批的展示内容与实际执行内容在安全相关部分实质一致（允许经定义的脱敏与无歧义格式变化）；
- **应判 inconclusive**：审批展示内容证据缺失，或任一侧证据／绑定不足以确立同一次审批与执行的对应关系。

核验钉规则面缺的正是这一类检查。相邻检查排除：command_injection.py 的判定面是命令如何被构造（注入构造本身），不读取审批展示面，不构成覆盖；channel_sender_verification.py 判发送方身份，与「所见＝所执行」无关；其余 18 插件主题（授权、凭证、路径钉住、模型工件、发送追踪等）与审批展示一致性无关，逐件对表后均不装下本展品（清单对表，见 5.1 落点）。

### 5.3 对我方系统的同类风险映射

我方工作面存在带审批的执行与发送动作（如 GitHub 写操作审批卡、外部消息发送确认），其审批展示与实际执行内容是否逐件在安全相关部分实质一致，本稿未逐件核——映射结论为风险提示级（未验证）：凡审批界面呈现摘要或占位、执行面按全文执行的环节，即与本件同型。建议动作见第六节 D-05，未核前我方各审批面的一致性状态记 UNKNOWN，不得据本节称已排查。
