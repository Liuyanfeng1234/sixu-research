## Executive summary

This report analyzes an approval-display-integrity event in the MCP tool mcp-ssh-manager: the `restart` option of its `ssh_deploy` tool runs on the remote server as a shell command, exactly as written, under the SSH user's identity — yet the human approval card does not show that command. The card reads only the tool name, "Destructive", and "(no command)"; the files being deployed and their target paths are not shown either. Per the repository-level advisory GHSA-vx67-5jmh-4xq2 (read in full in this round), the mechanism is a decoupling of the display layer from the execution layer: the approval engine sends the whole request (arguments complete, secrets removed) to the interface, but the interface renders only the `command` field, which a deploy request does not have. The approver therefore approves content they cannot see, and approval executes the unshown `restart` command. When the MCP client can be steered, for example by prompt injection, and the server's approval is set to `destructive` or `always`, a steered agent can smuggle an arbitrary command of its own into a deploy request and have it approved and executed. Affected versions are >=3.0.0, <=4.3.0 (the upper bound is carried over from the exam line's reading of the repository advisory API; see gap G-01 in Section 8), fixed in 4.3.1; no CVE identifier appears in the materials checked, and the severity is moderate. (Note: the triage original records "no CVE"; that means only that no CVE identifier appears in the materials checked, not that none exists; the triage score is unchanged.)

The coverage verdict for the V19 rule surface is **Not covered**: among the 20 registered plugins under the exam check pin (main-chain head 89a65525, re-read and confirmed unmoved via the connector in this round), no check judges "what the human reviewer sees = what is actually executed" — command_injection judges command construction and channel_sender_verification judges sender identity; neither judges consistency between approval display and executed content. The check shape this exhibit requires (proposed v19.approval.display_execution_mismatch) has not been merged into the main chain; this is a new gap, **SE24** (already queued in the loop backlog holding area), and the category "incomplete approval display" is a category the exam bank has not had before.

This report is **documentary evidence**: event facts rest on the GHSA advisory original (read in full in this round), corroborated by the v4.3.1 release notes for the affected lower bound and the fix behavior; the coverage conclusion is a static cross-check with **no live-run data** and must not be stated as a live-run detection.

## Key findings

- **KF-01 Mechanism established: approval display is decoupled from actual execution; the approver approves content they cannot see.** The engine sends the complete request, the interface displays only the `command` field; a deploy request has no such field, so the card shows only the tool name, "Destructive", and "(no command)", with the `restart` command, the deployed files, and their target paths all absent; approval then executes precisely the unshown `restart` command. Any request without a command line was displayed the same way. (Verified, primary source: GHSA advisory, Summary/Details sections)
- **KF-02 `restart` has always been a command and enters the remote command unquoted — but what makes this a vulnerability is the approval, not the command semantics.** Per the advisory's Details section, in `src/deploy-helper.js` the `restart` value goes into the remote command without quoting (the path, owner, and permissions have been quoted since 3.8.6), and the reporter's construction creates the file on the server; the advisory states this is reproducible (the specific construction is not restated in this report). The advisory is explicit, however, that `restart` has always been a command per the Deployment Guide, quoting it would break existing deployments, and the same attacker could already run any command via `ssh_execute` on an `unrestricted` server — the vulnerability is the invisibility at the approval step. - **KF-03 Exploitation conditions are narrow and their boundaries explicit.** The issue matters only when the server's approval is set to `destructive` or `always` and the MCP client can be steered (for example by a prompt injection in something the agent read); without approval there is no gain over `ssh_execute`; `readonly` and `restricted` servers refuse `ssh_deploy` altogether. (Verified, GHSA advisory Impact section)
- **KF-04 Coverage verdict: Not covered — the current head has no approval-display-integrity check.** In the check pin's 20-plugin list, no check judges consistency between approval display content and executed content using evidence from both sides. (Verified, static check, check pin 89a65525)

(Verified, exam bank criteria section + loop backlog entry SE24)
- **KF-06 The fix and workaround paths are explicit and carry primary-source pointers.** From 4.3.1 the approval card shows the arguments of a request that has no command line (the files, their target paths, the `restart` command), with secrets removed; `restart` keeps running as a command, and the tool description and guide now say so. Pre-upgrade workarounds: do not approve a request whose card reads "(no command)"; keep `readonly` or `restricted` on servers where an agent has no business deploying; or turn off the `advanced` tool group. (Verified, GHSA advisory Patches/Workarounds sections + v4.3.1 release notes)

## 3. Technical analysis

### 3.1 Mechanism: the display surface is decoupled from the execution surface, and the approval line fails at the "what is seen" link

Per the GHSA advisory original, the mechanism has three layers:

- **Tool semantics layer**: the `restart` option of `ssh_deploy` has always been, per the Deployment Guide, "a shell command run on the server exactly as written" — yet the tool description called it a service, so the semantic labeling and the actual behavior were already inconsistent.
- **Transport layer**: the approval engine sends the whole request — all arguments, with secrets removed — to the approval interface; the execution surface will act on this complete request.
- **Display layer**: the interface displayed only the `command` field of the request. A deploy request has no such field, so the card presented only the tool name, "Destructive", and "(no command)" — the `restart` command, the deployed files, and their target paths were all absent. When the approver approved, what executed was the `restart` command nobody had seen.

The point of characterization: the defect is not in command construction (`restart` being a command is by design); it is in the **decoupling of what the human reviewer sees from what they approve**. Human-in-the-loop approval serves as a line of defense against prompt injection only under the precondition that the approver can see the full executed content being approved; an incomplete display renders that line void (the exam bank's impact-surface formulation). The advisory also states that the same display logic applied to any other request without a command line, not only to `ssh_deploy`.

### 3.2 Exploitation conditions

- The target server's approval must be set to `destructive` or `always` (i.e., deploy requests enter human approval);
- The MCP client (the agent) must be steerable — the advisory's example is a prompt injection in something the agent read, causing it to embed a command of its own in a deploy request;
- The server's permission tier must not be `readonly` or `restricted` (both refuse `ssh_deploy` altogether);
- Boundary: without approval, an agent able to call `ssh_deploy` on an `unrestricted` server could already run any command via `ssh_execute`, so this case adds nothing there — its incremental risk lies exactly in the "approval enabled" scenario: content that approval should have stopped is passed because it is invisible.

### 3.3 Relation to similar events

This case differs from the exam bank's existing command-injection entries in its judgment surface: injection cases judge "how the command is constructed", while this case judges "whether what the human reviewer sees matches what is actually executed" — the same execution surface, a different defensive layer. The same product, mcp-ssh-manager, has two further command-injection advisories (GHSA-4jx9-2fwj-pg4j, database-helper command injection, and GHSA-qwwm-vrm9-4mw8, backup-subsystem command injection, first published at repository level on 2026-07-12 and 2026-08-28 respectively; not included in this exam window and noted for the record — see the daily summary's exclusion notes), showing that this product's command execution surface has failed repeatedly, but this case's category (approval display integrity) differs from theirs. This report makes category-level comparison only and does not retroactively affirm or alter any other entry's verdict.

### 5.2 Why it is not covered: which class of check is missing

The check shape this exhibit requires (i.e., the exam question's verdict requirements): for tool execution surfaces with a human approval step, judge using evidence from both the approval display and the actual execution —

- **Fail**: the approval display omits security-relevant content — the security-relevant parts of the actually-executed command / key parameters are not shown (placeholder or omission; defined harmless redaction is not an omission) while the execution surface executes the unshown content, with evidence from both sides complete and the display–execution binding to the same approval established (the exhibit itself, as recorded in the advisory, sits in this cell); where the binding or either side's evidence is insufficient, the case falls in the Inconclusive cell, not this one;
- **Pass (no false positive)**: for one and the same approval, the displayed content and the executed content agree in substance on all security-relevant parts (allowing defined redaction and unambiguous formatting changes);
- **Inconclusive**: approval-display evidence is missing, or the evidence or binding on either side is insufficient to establish that the display and the execution belong to the same approval.

The check pin's rule surface lacks exactly this class of check. Adjacent checks excluded: command_injection.py's judgment surface is how a command is constructed (the injection construction itself); it does not read the approval display surface and does not constitute coverage. channel_sender_verification.py judges sender identity, unrelated to "what is seen = what is executed". The remaining 18 plugins' themes (authorization, credentials, path pinning, model artifacts, outbound tracing, etc.) are unrelated to approval-display consistency; cross-checked item by item, none of them holds this exhibit (list cross-check; landing point in 5.1).
