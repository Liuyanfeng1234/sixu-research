## Executive summary

This report analyzes a stored cross-site scripting event in the WordPress plugin AI Puffer (AI Puffer – MCP Server for Claude & ChatGPT, with AI Chatbot; plugin slug: gpt3-ai-content-generator): an unauthenticated attacker submits a comment and induces the AI model to reproduce an HTML payload in its automatic reply; the plugin function insert_comment_reply_logic() insufficiently sanitizes the model output, stores the reply via wp_insert_comment(), and thereby bypasses the kses filtering that WordPress normally applies to comment content, so the stored script executes whenever any user visits the injected page (CVE-2026-130121). Affected versions are <=2.5.28; the fixed version is 2.5.29. Exploitation is not unconditional: the administrator must have configured the Comment Auto-Reply automation with Action on reply set to Approve (the default is Hold for moderation), and the attacker's comment must already have been approved — the bar is higher than for ordinary unauthenticated XSS, which is the main reason this item was triaged as grade B (significance score 1).

The coverage verdict for the V19 rule surface is **Not covered**, and it is doubly not covered. First, under the exam check pin (main-chain head 4a0db584, a historical check pin, not the current head), none of the 20 registered plugins makes any determination about "neutralization of stored/rendered content": full-text searches returned zero hits for the eight listed keywords (xss / cross-site / sanitiz / kses / innerhtml / dom / render / html), while neutraliz has 57 occurrences, none of which constitutes a web-content neutralization rule (see 5.1). Second, the adjacent check SE17 (v19.web_ui.unneutralized_supplied_content_rendering, corresponding to EXAM-20261114-10) had not been merged into the main chain under the historical check pin, and its frozen scope sets the fail gate on the condition that the content source is user-supplied; unneutralized model-generated content falls in its pass cell — in this item the content source is model-generated (indirectly influenced via the attacker's comment), so even if SE17 were merged under its current scope it would not judge fail. This subtype divergence must be checked together when SE17 is re-verified at landing; this draft must not prejudge coverage.

This draft is **documentary evidence**: the event facts are taken from primary-source documents (the Wordfence disclosure page was read and re-checked by the coordinator this round; in the L2 rework round the CVE record was re-checked by reading the official JSON via direct link, with the CNA disclosure time and the CVE record publication time listed separately and no longer conflated as a single "first made public"), and the coverage conclusion is a static cross-check, with **no live-run data**; it must not be described as a live-run detection.

## 3. Technical analysis

### 3.1 Mechanism: model output stored and rendered without neutralization

The plugin's Comment Auto-Reply automation calls an AI model to generate a reply after a comment is received. The defect lies in the absence of neutralization after the generation step: insert_comment_reply_logic() insufficiently sanitizes the model output and then stores the reply as a comment via wp_insert_comment(), thereby bypassing the kses filtering that WordPress normally applies to comment content. The attacker personally needs no account: the comment content they submit indirectly influences the model output and induces the model to reproduce an HTML payload in the reply; the payload is stored in the identity of an "AI reply," detached from the usual filtering surface on the user-input side, and executes in the browser of any user who visits the injected page, constituting stored XSS.

Two points of characterization. First, the content that is not neutralized originates from **model-generated content**, not from a field submitted directly by the attacker — even complete input-side filtering (against the comment body) cannot stop a payload that enters the database in the identity of a reply; the check surface must fall on "source-agnostic neutralization of content before storage/rendering." Second, what is bypassed is the platform's existing kses filtering: the defect is not "there is no filtering mechanism," but that this storage path does not pass through that mechanism — a path-bypass type of neutralization absence.

### 3.2 Exploitation conditions and bar

- The attacker needs no authentication and no legitimate credentials of any kind (primary source).
- The administrator must have configured the Comment Auto-Reply automation task, with Action on reply set to Approve; this item defaults to Hold for moderation, i.e., the administrator must have changed the default configuration (primary source, corrected by reading this round).
- The attacker's comment must already have been approved before the payload enters the auto-reply chain (primary source).
- Once all three prerequisites hold, the stored script executes whenever any user visits the injected page (primary source).

Accordingly, the reachable surface of this item is limited to the subset of sites that have "enabled AI auto-reply and set it to auto-approve," consistent with the triage significance score of 1 (long-tail plugin, high exploitation bar); but once the prerequisites hold, the execution surface is the browsers of all visitors, and the payload appears in the identity of the site's own AI reply, so the trust confusion is higher than for ordinary comment XSS — this point is an analytical judgment, not a primary-source assertion; see Section 8 for its evidence level.

### 3.3 Required verdict grid (exam-question scope)

V19 should detect "(model-generated or other) untrusted content stored and rendered on a page without neutralization" and judge fail, and a finding must cite the inspected content-neutralization evidence; a construction in which content is stored and rendered only after neutralization/filtering should not be falsely flagged (pass); missing neutralization evidence (unknown) should be judged inconclusive, not passed off as fail. The verdict must be **source-agnostic**: the same neutralization requirement applies to the three sources — user-supplied, model-generated, and system-assembled — which is exactly the divergence from the SE17 current frozen scope (fail only for user supply) (see Section 5). The actual state of this item: under the historical check pin there is no registered check that can perform the above verdict (see Section 5), and the verdict is Not covered.

### 5.3 Same-type risk mapping to our own systems

- Wherever an agent / AI application stores or renders **model-generated content** directly (comment auto-replies, AI customer-service answers posted back, summaries/titles auto-published, RAG results assembled into pages, etc.) and the storage/rendering path does not pass through neutralization filtering equal to that for user input, it is of the same type as this event; the risk point is not the model itself, but the pipeline assumption that "generated content is trusted by default and bypasses the input-side filtering surface."
- Our rule surface has no registered check for this surface under the historical check pin (see 5.1); a same-type inspection of our own in-use systems is an unverified recommendation, and until it is performed it is not recorded as inspected.

## 6. Detection and remediation recommendations (each marked with its evidence level)

1. Upgrade AI Puffer to 2.5.29 or a higher fixed version — **Verified** (advisory scope: the primary source explicitly states the fixed version and the Patched status; the remediation effect is a checked advisory statement, not a measured effect).
2. Before upgrading, keep / set Comment Auto-Reply's Action on reply back to Hold for moderation (the default), so AI replies pass human review first — **Unverified (interim mitigation)**: the primary source explicitly states that the default is Hold for moderation and that Approve is an exploitation prerequisite (this fact is Verified); the configuration mitigation derived from it has not been measured in this draft, and human review is not equivalent to content neutralization — approval does not guarantee the payload has been neutralized, and it must not be described as "safe after human approval."
3. Apply to model-generated content, before storage/rendering, neutralization filtering equal to that for user input (e.g., in a WordPress environment, ensure it passes kses-equivalent filtering), with the neutralization verdict not distinguishing the content source — **Unverified** (a recommendation derived from this item's mechanism and the exam-question verdict grid; not verified by a live run in this draft).
4. For other in-use AI reply / posting-back functions, perform a static inspection against the one question "does generated content bypass input-side filtering and get stored and rendered directly" — **Unverified** (a same-type inspection recommendation, not performed).
5. Detection surface: screen the stock of stored comments for records that originate from AI replies and contain HTML/script payloads — **Unknown** (the primary source gives no stock detection method; this is a general inference and must be checked separately before execution).
