## Executive summary

This report analyzes a file-tool path-confinement failure in the AI coding agent JetBrains Junie CLI: Junie CLI's agent file tools did not confine write targets to the current project directory, so files outside the project directory could be modified (CVE-2026-133195, CWE-73). Per the JetBrains CNA CVE record original (cvelistV5, read directly in the re-check round on 2026-11-20), the affected scope is Junie CLI before 26.6.29 (version bound lessThan 26.6.29, defaultStatus unaffected, i.e., not affected from 26.6.29 onward; the record has no separate "fixed version" field), the CVSS 3.1 score is 7.5, and the record publication time is 2026-11-19T14:50:14.338Z. The event mechanism is stated only to the extent of the CNA record's description: the CNA record as read carries no PoC, and how an attacker induces the agent to write to a specific path outside the project has not been made public; this draft marks each such point unknown and does not fill it in by inference (see Section 8).

The coverage verdict for the V19 rule surface is **Not covered**: among the 20 registered plugins under the exam check pin (main-chain head 4fcf68b4, a historical check pin, not the current head), there is no SE20 check as defined by EXAM-20261117-02 (v19.filesystem.unconfined_tool_write_path) — that check had not been merged into the main chain at the check-pin point in time (the current-head state was not re-checked and is not retroactively asserted), and the actually retrieved plugin list contains no output_path_confinement.py. The adjacent check v19.filesystem.path_validation_without_pinning (SE6) judges validation-to-use pinning (TOCTOU) and, under the same scope as EXAM-20261117-02, does not count as coverage of this surface. This gap is the same gap as EXAM-20261117-02 and is already queued in the loop backlog area **SE20**; this entry does not queue it again and only adds this event under the SE20 entry.

This draft is **documentary evidence**: all event facts rest on the JetBrains CNA CVE record original (the cvelistV5 original was read directly in the re-check round); The Injection is a third-party restatement and interpretation (a secondary source), used only as corroboration and not as a vendor verification page; the coverage conclusion is a static cross-check, with **no live-run data**, and must not be described as a live-run detection.

## 3. Technical analysis

### 3.1 Mechanism: file-tool write paths are not pinned inside the project directory

Per the exam bank exam-question section: the coding agent's file tools did not confine write targets to the current project directory, so files at paths outside the project could be modified. The point of characterization is the write boundary: the file tools are an **execution-surface capability** of the coding agent (they write changes to disk directly), and the project directory is the **expected scope** the user grants that capability; when a write path lands on disk without a directory-confinement check, the scope is decided by the path on the processed-content side rather than by the user — this is exactly the characterization of CWE-73: the file name or path the program touches is controlled by input external to the program. The bounded authorization "let the agent work in this project" is amplified into a modification surface over files outside the project directory; whether local configuration and credential-class files were actually affected is not stated in the record as read and is not verified (a same-type inference in the exam bank impact section, not taken as a verified fact).

This draft's statement of the mechanism is limited to the CNA record's description: the CNA record as read carries no PoC and does not disclose through what content or instruction construction the agent was induced to write outside the project, nor whether there was any confirmation step before the write (G-01); accordingly, no specific inducing steps are written, and the exploitation conditions are recorded only per the record and the vector verbatim (AV:N / PR:N / UI:R reproduced verbatim; UI:R does not prove the number or form of interactions, and AV:N does not prove the CLI's network-service form).

### 3.2 Distinction from the other three Junie items in the same batch

The same disclosure batch contains four Junie events; their write/execution channels differ, their coverage verdicts differ, and they are not merged: (1) this item, CVE-2026-133195, file tools writing directly outside the project directory (SE20, not covered, TB-018); (2) CVE-2026-133196, shell output redirection overwriting files outside the project (the same SE20 gap plus a subtype divergence, TB-019); (3) CVE-2026-133197, command injection via file names during code review (the class matches an existing command-injection check, but the construction details have not been disclosed and it is recorded as not checked, TB-020 candidate); (4) CVE-2026-133198, project-file terminal configuration driving code execution (a new class and a new gap, SE23, TB-021). The common surface of the four is "the input trust boundary of coding agents," but the check forms differ — path confinement, redirection channels, command-construction neutralization, configuration trust confirmation — and the merging of any one check does not automatically cover the other three. This item and item (2) both belong to SE20, but their write channels differ (file-tool direct write / shell redirection); whether item (2)'s subtype fits at SE20 landing re-verification is unrelated to this item and they do not retroactively certify each other.

### 3.3 Exploitation conditions

- The target must be using an affected version of Junie CLI (before 26.6.29).
- Per the public vector verbatim: UI:R (user interaction required; the number and specific form are not disclosed), PR:N (no privileges required), AC:H (high complexity); "the developer points the agent at externally supplied content" is The Injection's interpretation (a secondary source), which this draft uses only as corroboration and not as a verified fact.
- The specific construction by which an attacker induces the agent to write outside the project is not disclosed in the materials relied on (unknown); this section is not filled in with conventions from similar products.

### 5.2 Why not covered: which class of check is missing

The check form this exhibit requires (i.e., the exam-question verdict requirement): a directory-confinement determination on the inspected object's tool file-write paths —

- **Should judge fail**: a tool write path is not confined to the expected directory (a finding must cite the inspected write-path evidence);
- **Should judge pass (no false flag)**: the write path, after normalization, is pinned inside the project directory, and out-of-bounds writes are refused;
- **Should judge inconclusive**: write-path evidence is missing, not passed off as fail.

What the rule surface under the check pin lacks is exactly this class of check; its proper form is the SE20 check (v19.filesystem.unconfined_tool_write_path, the frozen scope of EXAM-20261117-02), which had not been merged into the main chain at the check-pin point in time; the carrier state is likewise stated at the check-pin point in time, and the current head and the carrier's current state were not re-checked and are not retroactively asserted. Reasons for excluding adjacent checks: v19.filesystem.path_validation_without_pinning (SE6) judges validation-to-use pinning (TOCTOU) — a path that is swapped between validation and use falls in its exhibit, whereas this item's writes were never confined to the directory from the start and there is no "drift after validation" construction, so under the same scope as EXAM-20261117-02 it does not count as coverage; the archive member plan surface and the pipeline self-protection path_escape take our own pipeline and the archive surface, not the inspected object's file-tool write surface, as their verdict objects, and likewise do not count as coverage (exam bank standard-section scope).

### 5.3 Same-type risk mapping to our own systems

Our own agent work surfaces likewise write to the local machine with file tools (there are on-disk actions both inside and outside the workspace): any surface where "the tool write path is decided by task content and is not pinned by a directory scope" is of the same type as this item. The mapping conclusion is at the risk-alert level (unverified): we have not yet performed a same-type live-run check of our own file-tool write surfaces, and this section must not be used to claim they have been inspected; the recommended action is at D-04 in Section 6.
