## 执行摘要

本报告分析主流本地推理引擎 llama.cpp 的一起模型加载器内存安全事件：其 hrm_text 架构加载器的 load_arch_hparams() 存在整数溢出（CVE-2026-133710，CWE-190），攻击者构造 GGUF 模型文件元数据，使派生运算整数溢出、绕过块数检查，随后 load_arch_tensors() 把张量指针写出 model.layers 数组边界之外；受影响加载器处理该不可信模型文件时可能发生堆内存破坏，代码执行是潜在后果。据 CVE 记录原文（VulnCheck CNA，本拍经 CVE Services 接口实读全文），受影响版本为 b11003 起、<b12556（记录版本段 version b11003、lessThan b12556），b12556 为修复发布；CVSS 3.1 评分 7.8（向量 AV:L/AC:L/PR:N/UI:R/S:U/C:H/I:H/A:H），同记录另载 CVSS 4.0 评分 8.5。考卷库所载关键数（受影响 b11003–<b12556、b12556 修复、CVSS 3.1 7.8、CWE-190、公开时点 2026-11-20T12:17:08Z）已逐项与 CVE 记录原文对平（见第七节）。

对 V19 规则面的覆盖判定为**未覆盖**：考卷核验钉（主链头 89a65525，2026-11-21 每日考卷核验钉）下 20 个在册插件中，model_artifact_integrity 只核模型权重差分与来源哈希声明，不判加载器按元数据派生尺寸的整数溢出与分配／写入边界一致性——本件所需检查形态（拟 v19.model.loader_metadata_bounds）未合入主链，为新缺口 **SE25**（已入 loop backlog 在队区）。判定口径为加载面摘要级：只判「元数据派生分配可回绕且边界不一致＝fail／派生尺寸经溢出检查且边界一致＝pass 不误报／边界处理证据缺失＝inconclusive」三格，不做二进制内存安全分析。

## 关键发现

- **KF-01 机理成立：元数据派生尺寸可溢出，检查与写入按两套数走。** load_arch_hparams() 以 GGUF 元数据派生块数时发生整数溢出，块数检查所依据的派生值与实际写入计数脱钩（检查依据的派生值通过检查）；load_arch_tensors() 随后按与检查不一致的计数把张量指针写出 model.layers 边界，堆越界写成立。（已验证，一手源：CVE 记录描述段原文）
- **KF-02 利用形态是「模型文件即不可信输入」的又一实证。** 攻击向量为本地（AV:L）、需用户交互（UI:R）：受影响加载器处理特定不可信模型文件时可能发生内存破坏，代码执行是潜在后果。CVSS 向量记无需权限（PR:N）——此为向量口径，不外推实际部署环境的权限形态。GGUF 为 llama.cpp 的模型文件格式，加载第三方模型文件是本地推理的使用形态；其流通广度本稿未核，不作普及断言。（已验证，CVE 记录 CVSS 向量与描述段）
- **KF-03 覆盖判定为未覆盖：现头无加载器元数据边界检查。** 核验钉 20 插件清单中 model_artifact_integrity.py 在册，但其判定面为止于权重差分与来源哈希声明，不含元数据派生边界与整数溢出判定。（已验证，静态核验，核验钉 89a65525）
- **KF-04 本件为新类别新缺口 SE25，不是已有缺口的新事件。** 考卷库此前无「模型加载器元数据边界／整数溢出」类别；拟建检查 v19.model.loader_metadata_bounds 已入 loop backlog 在队区，本稿不预判其落地形态与覆盖。（已验证，考卷库标准段＋loop backlog SE25 条）

## 三、技术分析

### 3.1 机理：派生尺寸回绕使「检查的数」与「写入的数」脱钩

据 CVE 记录描述段原文：hrm_text 加载器的 load_arch_hparams() 在以 GGUF 元数据派生架构参数时存在整数溢出——派生运算溢出使块数检查所依据的数值与后续写入计数脱钩，从而绕过块数检查（block count check）；随后 load_arch_tensors() 把张量指针写出 model.layers 数组之外，可能破坏堆内存，代码执行是潜在后果。

定性要点在「分配／检查口径与写入计数不一致」：块数检查面对的派生值与实际写入面对的计数不一致（前者通过检查、后者逐层写指针），两者脱钩即越界。这类缺陷的判定面不在某个单点运算是否溢出，而在**派生尺寸的全链一致性**：凡尺寸由不可信元数据派生，必须在派生点做溢出检查、且分配尺寸与写入边界共用同一已检值。本稿对机理的陈述以 CVE 记录描述段为限：记录未附 PoC、未披露具体构造数值与触发该加载器所需的模型架构细节，故不写具体构造步骤（见第八节 G-01）。

范围限定：缺陷位于 hrm_text 架构加载器路径。本稿不把结论外推为「一切 GGUF 加载皆受影响」——受影响的是经该加载器加载的模型路径；其余架构加载器是否存在同型派生问题，所读一手源未载，未知（见第八节 G-05）。

### 3.2 利用条件

- 目标须运行受影响版本（b11003 起、<b12556）的 llama.cpp，并以 hrm_text 加载器路径处理不可信 GGUF 模型文件；受影响加载器处理该文件时可能发生内存破坏，代码执行是潜在后果；
- 攻击者须能向受害者提供构造的 GGUF 模型文件（模型分享、社区仓库、供应链投递等途径为影响面推断，一手源未指定投递渠道）；
- 向量口径：本地向量（AV:L）、低复杂度（AC:L）、无需权限（PR:N，此为 CVSS 向量口径，不外推实际部署环境的权限形态）、需用户交互（UI:R，即加载动作本身）。CVSS 4.0 向量记 UI:P（被动交互），两向量对交互的刻画粒度不同，本稿并记、不调和。

### 3.3 与同类事件的关系

考卷库影响面段记：本件与 EXAM-20261116-02（vLLM 竞态）同属「推理引擎本体缺陷面」。共性口径是：推理引擎把模型文件与模型元数据当可信输入处理，而模型文件实际经第三方流通——「权重文件不是数据、是可执行等价输入」这一口径在本件再次成立。本稿只作类别层面对照，不对 EXAM-20261116-02 的判定作任何追认或改判。

### 5.1 核验方法与核验钉

- 核验钉：主链头 `89a655254f247a95dbf24fb4213c0e33076b018a`（cursor/production-did-labels-e95a，2026-11-21 每日考卷实读，顶提交为 #498 合并）——此为考卷核验时点钉。规则面为该钉下 20 插件；20 件固定清单（文件名／blob sha／大小）随本报告公开版同行发布（公开仓 sixu-research `reports/TB-025/evidence/plugins-list-20-pin-89a65525.md`），20 件 blob sha 与大小与 2026-11-20 钉版逐件全等、无新增检查合入。
- 检索结果：实取清单含 model_artifact_integrity.py（14,277 B）；20 插件无加载器元数据边界／整数溢出主题检查（考卷库核验证据落点段）。

### 5.2 为何未覆盖：缺哪一类检查

本展品需要的检查形态（即考题判定要求）：对模型文件加载面的元数据边界摘要判定——

- **应判 fail**：加载器按模型文件自带元数据派生分配尺寸且派生运算可回绕／溢出、分配与写入边界不一致（本件本体）；
- **应判 pass（不误报）**：元数据派生尺寸经溢出检查、且写入边界与分配一致；
- **应判 inconclusive**：加载器边界处理证据缺失。

核验钉规则面缺的正是这一类检查。现头 model_artifact_integrity 的判定面是模型工件本体（权重差分、来源哈希声明），回答的是「工件是否被换、来源是否对得上」，不回答「加载器吃下这份元数据时会不会写出界」——两者是工件面与加载面之别，不构成覆盖。相邻检查排除：path_validation_pinning.py 判路径校验—使用钉住（TOCTOU），与元数据派生边界无关，不计覆盖；其余 18 插件主题（授权、注入、凭证、发送者核验等）与加载面无关，逐件对表后均不装下本展品（20 件逐件排除表随本报告公开版同行发布（公开仓 sixu-research `reports/TB-025/evidence/adjacent-exclusion-table.md`），逐件列判定面与排除理由，见 5.1 指针）。
