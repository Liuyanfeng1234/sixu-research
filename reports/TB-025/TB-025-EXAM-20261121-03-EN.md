## Executive summary

This report analyzes a memory-safety event in the model loader of llama.cpp, a mainstream local inference engine: the load_arch_hparams() function of its hrm_text architecture loader contains an integer overflow (CVE-2026-133710, CWE-190). An attacker crafts GGUF model-file metadata so that the derivation overflows as an integer operation and bypasses the block count check; load_arch_tensors() then writes tensor pointers past the boundary of the model.layers array. When an affected loader processes such an untrusted model file, heap memory corruption may occur, and code execution is a potential consequence. Per the CVE record original (VulnCheck CNA; read in full in this round via the CVE Services API), the affected versions are b11003 up to but not including b12556 (record version entry: version b11003, lessThan b12556), b12556 is the fixing release, the CVSS 3.1 score is 7.8 (vector AV:L/AC:L/PR:N/UI:R/S:U/C:H/I:H/A:H), and the same record also carries a CVSS 4.0 score of 8.5. The key figures carried in the exam bank (affected b11003–<b12556, fixed in b12556, CVSS 3.1 7.8, CWE-190, publication time 2026-11-20T12:17:08Z) have been reconciled item by item against the CVE record original (see Section 7).

The coverage verdict for the V19 rule surface is **Not covered**: among the 20 registered plugins under the exam check pin (main-chain head 89a65525), model_artifact_integrity checks only model weight differentials and source-hash declarations; it does not judge integer overflow in loader-derived sizes from metadata, nor allocation/write boundary consistency. The check shape this exhibit requires (proposed v19.model.loader_metadata_bounds) has not been merged into the main chain; this is a new gap, **SE25** (already queued in the loop backlog holding area). The verdict scope is loader-surface summary level: fail where metadata-derived allocation can wrap and boundaries are inconsistent / pass (no false positive) where derived sizes pass overflow checks and boundaries are consistent / inconclusive where boundary-handling evidence is missing. No binary memory-safety analysis is performed.

This draft is **documentary evidence**: event facts rest on the CVE record original (read directly in this round); the VulnCheck advisory page was read for its full description paragraph, and structured fields follow the CVE record of the same CNA (see G-02 in Section 8); the coverage conclusion is a static cross-check, with **no live-run data**, and must not be described as a live-run detection.

**Key numbers**: affected b11003–<b12556 | fixed b12556 | CVSS 3.1 7.8 (also CVSS 4.0 8.5) | 20 plugins registered under the check pin, 0 checks that subsume this exhibit | triage grade A, 14/18 | gap number SE25 (newly established gap) | end-to-end live-run receipts 0.

(Verified, primary source: description paragraph of the CVE record original)
- **KF-02 The exploitation shape is another substantiation of "a model file is untrusted input."** The vector is local (AV:L) with user interaction required (UI:R): when an affected loader processes a specific untrusted model file, memory corruption may occur, and code execution is a potential consequence. The CVSS vector records no privileges required (PR:N) — this is vector scope and is not extrapolated to the privilege shape of actual deployments. GGUF is llama.cpp's model-file format, and loading third-party model files is a mode of local inference; the breadth of its circulation has not been checked in this draft and no prevalence claim is made. ## 3. Technical analysis

### 3.1 Mechanism: the derived size wraps, decoupling "the checked number" from "the written number"

Per the description paragraph of the CVE record original: in the hrm_text loader's load_arch_hparams(), an integer overflow exists in the derivation of architecture parameters from GGUF metadata — the derivation from the metadata carried in the GGUF file overflows as an integer operation, so that the value the block count check relies on decouples from the count actually written, thereby bypassing the block count check; load_arch_tensors() then writes tensor pointers past the boundary of the model.layers array, and heap memory corruption may occur, with code execution as a potential consequence.

The characterization point is the inconsistency across the whole derivation chain: the derived value the block count check faces is inconsistent with the count the actual writes face (the former passes the check; the latter writes pointers layer by layer); once the two decouple, the out-of-bounds write follows. The verdict surface for this defect class is therefore not whether any single operation overflows, but the **end-to-end consistency of derived sizes**: wherever a size is derived from untrusted metadata, the derivation point must carry an overflow check, and the allocation size and the write boundary must share the same checked value. This draft states the mechanism only to the extent of the CVE record's description paragraph: the record carries no PoC and does not disclose specific crafted values or the model-architecture details needed to reach this loader; no concrete construction steps are written here (see Section 8, G-01).

Scope limitation: the defect sits in the hrm_text architecture loader path. This draft does not extrapolate the conclusion to "all GGUF loading is affected" — what is affected is the model path loaded through this loader; whether other architecture loaders carry the same derivation pattern is not stated in the primary sources read and is unknown (see Section 8, G-05).

### 3.2 Exploitation conditions

- The target must run an affected llama.cpp version (b11003 up to but not including b12556) and process an untrusted GGUF model through the hrm_text loader path; when the affected loader processes such a file, memory corruption may occur, and code execution is a potential consequence;
- The attacker must be able to supply the victim with a crafted GGUF model file (delivery channels such as model sharing, community repositories, or supply-chain delivery are impact-scope inferences; the primary source does not name a delivery channel);
- Vector scope: local vector (AV:L), low complexity (AC:L), no privileges required (PR:N — this is CVSS vector scope and is not extrapolated to the privilege shape of actual deployments), user interaction required (UI:R — the loading action itself). The CVSS 4.0 vector records UI:P (passive interaction); the two vectors characterize interaction at different granularity, and this draft records both without reconciling them.

### 3.3 Relation to events of the same class

The exam bank's impact section records that this case and EXAM-20261116-02 (a vLLM race condition) belong to the same "inference-engine intrinsic defect surface." The shared characterization is that inference engines treat model files and model metadata as trusted input, while model files in fact circulate through third parties — the position that "a weight file is not data but executable-equivalent input" holds again in this case. This draft makes the comparison at category level only and neither retroactively asserts nor revises any verdict of EXAM-20261116-02.

### 5.2 Why not covered: which class of check is missing

The check shape this exhibit requires (i.e., the exam question's verdict requirements) is a metadata-bounds summary verdict over the model-file loading surface:

- **Fail**: the loader derives allocation sizes from metadata carried in the model file itself, the derivation can wrap / overflow, and the allocation and write boundaries are inconsistent (the present exhibit itself);
- **Pass (no false positive)**: metadata-derived sizes pass overflow checks and the write boundary is consistent with the allocation;
- **Inconclusive**: loader boundary-handling evidence is missing.

What the check-pin rule surface lacks is exactly this class of check. The current head's model_artifact_integrity has as its verdict surface the model artifact itself (weight differentials, source-hash declarations); it answers "was the artifact swapped, and does the source check out," not "will the loader write out of bounds when it consumes this metadata" — the two are the artifact surface and the loading surface respectively, and the former does not constitute coverage of the latter. Adjacent checks excluded: path_validation_pinning.py judges path validation-to-use pinning (TOCTOU) and is unrelated to metadata-derived bounds, so it does not count as coverage; the remaining 18 plugins' themes (authorization, injection, credentials, sender verification, etc.) are unrelated to the loading surface and, after item-by-item cross-check against the list, none of them subsumes this exhibit (the item-by-item exclusion table for all 20 plugins is published with this report in the public repository sixu-research, at `reports/TB-025/evidence/adjacent-exclusion-table.md`, each with its verdict surface and exclusion rationale; see the pointer in 5.1).

### 5.3 Same-type risk mapping onto our own systems

Our own work surface includes local inference and model-file handling scenarios, but this draft has not checked the actual inference engines and version composition we deploy — whether we run an affected llama.cpp version, and whether we load third-party GGUF files, are both UNKNOWN, and this section must not be read as stating that we have either cleared or been hit. The mapping conclusion is at risk-alert level (unverified): the position that model files are treated as untrusted input (source verification + isolated loading) should enter our model-artifact handling checklist; recommended actions are in Section 6, D-04.
