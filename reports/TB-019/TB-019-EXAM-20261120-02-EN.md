## Executive summary

This report analyzes a write-channel path-confinement failure in the AI coding agent JetBrains Junie CLI: Junie CLI wrote content outside the project directory via shell output redirection, overwriting files outside the project (CVE-2026-133196). The key distinction from CVE-2026-133195 in the same batch (file tools writing directly out of bounds) is the write channel: this item is not a file-tool direct write but shell redirection — the same missing directory confinement holds through a second channel. Per the JetBrains CNA CVE record original, the affected scope is Junie CLI before 26.11.1, not affected from 26.11.1 onward (version bound lessThan 26.11.1, defaultStatus unaffected; the record has no separate "fixed version" field), and the public date is 2026-11-19 (datePublished 2026-11-19T14:50:14.933Z); the CVSS 3.1 score of 5.3 and CWE-184 were obtained by reading the CNA record original directly (cvelistV5) in the re-check round, and the exam bank entry does not carry these two numbers (see Section 8, G-03). The CNA record as read carries no PoC, and the specific form of the redirection and its triggering construction have not been disclosed; this draft marks each such point unknown (see Section 8).

The coverage verdict for the V19 rule surface is **Not covered**: under the exam check pin (main-chain head 4fcf68b4, a historical check pin, not the current head), this exhibit is tracked under the SE20 check (v19.filesystem.unconfined_tool_write_path), but that check had not been merged into the main chain (the actually retrieved plugin list contains no output_path_confinement.py); the redirection subtype must be checked separately when SE20 lands, and this report does not prejudge whether that check can judge this subtype. This item additionally carries a **subtype divergence**: the SE20 frozen scope's independent observed-out-of-bounds fail branch takes "tool write paths" as its surface, and whether the shell output redirection channel fits within it must be checked together at SE20 landing re-verification — this draft does not prejudge that this subtype will be covered once SE20 lands, and records the verdict only as Not covered. This gap is the same gap as EXAM-20261117-02 and is already queued in the loop backlog area **SE20**; this entry does not queue it again and only adds this event and the subtype divergence under the SE20 entry.

This draft is **documentary evidence**: all event facts rest on the JetBrains CNA CVE record original (the cvelistV5 original was read directly in the re-check round); Noroxi is listed only as mirror corroboration and is not a factual basis; the coverage conclusion is a static cross-check, with **no live-run data**, and must not be described as a live-run detection. It must also be recorded: the source link listed in the exam bank entry points to a different CVE record (CVE-2026-123315) and is not a factual basis for this item; see Section 8, G-01.

## 3. Technical analysis

### 3.1 Mechanism: shell redirection is a second write channel not covered by directory confinement

Per the exam bank exam-question section: the coding agent wrote content outside the project directory via shell output redirection, overwriting files outside the project; the write channel is not a file-tool direct write but shell redirection. The point of characterization is channel completeness: a coding agent's write surface has at least two channels — file-tool direct writes and shell command execution (redirection and pipe-to-disk both belong to it). If directory confinement is applied only to the file-tool surface, the shell channel becomes a bypass: the same constraint "writes must be pinned inside the project directory" holds only if it holds separately for every write channel. That is exactly what this item substantiates — what is affected is not some file tool's path validation, but the redirection targets on the shell execution surface not being under the same confinement.

This draft's statement of the mechanism is limited to the CVE record's description: the specific form of the redirection (what shell construction, whether it must combine with a specific command), whether the agent's shell execution itself has a sandbox and a confirmation step, and the permission context of the overwrite are all undisclosed in the materials relied on (G-02); accordingly, no specific triggering steps are written, and only "overwriting files outside the project via shell output redirection" is recorded as the primary-source claim.

### 3.2 Distinction from the other three Junie items in the same batch

The same disclosure batch contains four Junie events; their write/execution channels differ, their coverage verdicts differ, and they are not merged: (1) CVE-2026-133195, file tools writing directly outside the project directory (SE20, not covered, TB-018); (2) this item, CVE-2026-133196, shell output redirection overwriting files outside the project (the same SE20 gap plus a subtype divergence, TB-019); (3) CVE-2026-133197, command injection via file names during code review (the class matches an existing command-injection check, but the construction details have not been disclosed and it is recorded as not checked, TB-020 candidate); (4) CVE-2026-133198, project-file terminal configuration driving code execution (a new class and a new gap, SE23, TB-021). This item's relation to (1) is the closest: both belong to SE20 and both are a missing directory confinement, but the channels differ — if at SE20 landing only item (1)'s file-tool surface is built, whether this item's channel is subsumed must be checked separately; that is exactly the subtype divergence recorded in the exam bank, and it does not dissolve automatically from sharing the gap.

### 3.3 Exploitation conditions

- The target must be using an affected version of Junie CLI (before 26.11.1).
- Per the public vector verbatim: UI:R (user interaction required; the number and specific form are not disclosed), PR:N (no privileges required), AC:H (high complexity), AV:N (vector notation; not used here to assert the CLI's network-service form); the impact surface is recorded per the vector verbatim as C:N/I:H/A:N, and no on-site impact is asserted from it. The subsequent use of an overwritten file can amplify the consequences — that amplification chain is an inference and is marked unverified in this draft.
- The specific construction by which an attacker induces the agent to execute a shell command with an out-of-bounds redirection is not disclosed in the materials relied on (unknown).

### 5.2 Why not covered: which class of check is missing + the subtype divergence

The check form this exhibit requires (i.e., the exam-question verdict requirement): a directory-confinement determination on the inspected object's write paths, where the verdict surface must include the shell redirection channel —

- **Should judge fail**: a write path is not confined to the expected directory (the redirection channel); a finding must cite the inspected write-path evidence;
- **Should judge pass (no false flag)**: the redirection target, after normalization, is pinned inside the project directory, or the out-of-bounds redirection is refused;
- **Should judge inconclusive**: write-path evidence is missing, not passed off as fail (the exam-question section does not list this cell separately; it is recorded per this line's unified scope).

The non-coverage has two layers: first, the SE20 check itself had not been merged into the main chain, and no check in the rule surface under the check pin makes a directory-confinement determination on write paths at all (the same as TB-018); second, the subtype divergence — the SE20 frozen scope (EXAM-20261117-02) takes "tool write paths" as the surface of its independent observed-out-of-bounds fail branch, whose evidence form is the file tools' write paths; a shell redirection's write path is hidden inside the command construction, and whether it falls within that branch's evidence scope is expressly recorded in the exam bank as "to be checked together at SE20 landing re-verification; coverage must not be prejudged." Accordingly, this draft's verdict stops at Not covered: it says no more on account of the check not being merged, and does not pre-certify post-landing coverage on account of sharing the gap.

### 5.3 Same-type risk mapping to our own systems

Our own agents write files via shell every day (command redirection to disk is a routine working method): any surface where "the shell write target is decided by task content and is not checked against a directory scope" is of the same type as this item, and closer to home than the file-tool surface. The mapping conclusion is at the risk-alert level (unverified): we have not yet performed a same-type live-run check of our own shell write surfaces, and this section must not be used to claim they have been inspected; the recommended action is at D-04 in Section 6.
